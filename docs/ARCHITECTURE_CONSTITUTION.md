# Architecture Constitution

المبدأ المعماري الأعلى: «نبني MVP منخفض التكلفة، ولكن بمعمارية قابلة للتوسع والاستبدال.»

- **القاعدة 1:** النظام Multi-Tenant من الناحية المعمارية منذ البداية.
- **القاعدة 2:** بيانات كل شركة/متجر يجب أن تكون معزولة عن بيانات الشركات الأخرى.
- **القاعدة 3:** قلب الوكيل AI لا يرتبط مباشرة بمصدر بيانات واحد.
- **القاعدة 4:** Google Sheets هو مصدر بيانات أولي محتمل للـMVP، وليس شرطاً أن يكون قاعدة البيانات النهائية.
- **القاعدة 5:** يجب إنشاء طبقة تجريد لمصادر البيانات (Data Provider / Repository Abstraction) بحيث يمكن مستقبلاً الانتقال من Google Sheets إلى Supabase / PostgreSQL / MySQL / ERP / نظام محاسبي / API خارجي دون إعادة بناء منطق الوكيل.
- **القاعدة 6:** يجب فصل قناة التواصل عن قلب الوكيل، بحيث يمكن دعم Web, WhatsApp, Telegram, Messenger وغيرها مستقبلاً.
- **القاعدة 7:** يجب فصل مزود الذكاء الاصطناعي عن منطق التطبيق. يجب ألا يصبح النظام معتمداً معمارياً على مزود AI واحد.
- **القاعدة 8:** يجب تصميم API من البداية ليكون طبقة تكامل رسمية.
- **القاعدة 9:** أي نظام خارجي يجب أن يتصل عبر Integration Layer أو API Contract واضح.
- **القاعدة 10:** لا يجوز اختراع بيانات للعميل. إذا كانت معلومة السعر أو المخزون أو سياسة المتجر غير موثوقة أو غير موجودة، يجب أن يتصرف الوكيل وفق سياسة عدم المعرفة أو التحويل للبشر.
- **القاعدة 11:** لا يتم حذف بنية أساسية سليمة فقط لتسهيل تنفيذ ميزة مؤقتة.
- **القاعدة 12:** أي تغيير معماري مهم يجب تسجيله في `DECISION_LOG.md`.
- **القاعدة 13:** لا تنفذ طلباً يؤدي إلى كسر مبدأ معماري سابق دون تسجيل قرار جديد يوضح سبب التغيير.
- **القاعدة 14:** الوثائق جزء من المشروع وليست ملفات ثانوية.
